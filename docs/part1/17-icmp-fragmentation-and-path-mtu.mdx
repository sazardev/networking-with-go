# ICMP, Fragmentation, and Path MTU

IP promises to deliver a packet on a best-effort basis. It does not promise that the packet fits, that it will arrive, or that anyone will tell you why it did not. The protocol that fills that last gap is **ICMP**, the Internet Control Message Protocol. It is not a transport protocol, it does not carry application data, and it has no ports. It is the network's way of saying "that did not work, and here is roughly why."

Most people meet ICMP through `ping`. That is a shame, because the same protocol is what makes `traceroute` work, what lets a sender discover the largest packet a path can carry, and what silently breaks when a firewall blocks it. This chapter covers all three.

### A Control Protocol, Not a Data Protocol

An ICMP message is carried directly inside an IP packet, with protocol number 1 for ICMPv4 and 58 for ICMPv6. The message has a type, a code, a checksum, and a payload that depends on the type.

The common types are worth knowing by number, because packet captures and firewall rules use the numbers:

| Type | Name | What it means |
|---|---|---|
| 0 | Echo reply | The answer to a ping |
| 3 | Destination unreachable | The network, host, or port could not be reached |
| 5 | Redirect | Use a different gateway for this destination |
| 8 | Echo request | The ping itself |
| 11 | Time exceeded | The TTL reached zero |

Type 3 carries a **code** that narrows the reason: code 0 is network unreachable, code 1 host unreachable, code 3 port unreachable, and code 4 is the one this chapter cares about most — **fragmentation needed, but the Don't Fragment bit was set**.

### TTL, Ping, and Traceroute

Every IP packet carries a **TTL** field. Each router decrements it by one; a router that reaches zero drops the packet and sends back an ICMP Time Exceeded message to the source. The field exists to stop packets from looping forever if routing tables are wrong.

`ping` sends an Echo Request and waits for an Echo Reply. It measures round-trip time and reports loss. That is genuinely all it does. It does not test a web server, a database, or a port — only whether ICMP can make the round trip.

`traceroute` abuses the TTL mechanism deliberately. It sends a packet with TTL 1, receives Time Exceeded from the first router, then sends TTL 2, receives it from the second, and so on. Each router that drops an expired packet reveals its address. The result is a hop-by-hop map of the path, built entirely out of error messages.

<Warning title="A blocked ping does not mean a dead host">Many servers and firewalls drop ICMP while serving HTTPS perfectly. Others answer ping while the service behind them is down. Ping tests one thing: ICMP reachability. If you need to know whether a service is reachable, test the actual port with `curl`, `nc`, or a small connection attempt. This is one of the most common false conclusions in troubleshooting.</Warning>

### Fragmentation: When a Packet Is Too Big

Every link has a **Maximum Transmission Unit**, the largest frame payload it can carry. Ethernet's default is 1500 bytes. A packet larger than the MTU cannot cross the link in one piece, so IPv4 gives routers two options: fragment it, or drop it and tell the sender.

Fragmentation splits the payload into pieces, each with its own IP header, a shared **identification** field, a **fragment offset**, and the **More Fragments** flag. The destination reassembles them. The pieces can take different paths and arrive out of order; the receiver uses the identification and offset to rebuild the original packet.

```
Original packet:  [IP hdr][        3500 bytes of payload        ]
Fragments:        [IP hdr][ 1480 B ][MF=1][offset 0]
                  [IP hdr][ 1480 B ][MF=1][offset 185]
                  [IP hdr][  540 B ][MF=0][offset 370]
```

Fragmentation works, but it is expensive: more headers, more packets, more chances to lose a piece. Losing one fragment loses the whole datagram, because IP has no retransmission. It also puts reassembly work on the receiver, which is a denial-of-service vector if an attacker sends many incomplete fragments.

### Path MTU Discovery

The better approach is to avoid fragmentation entirely. A sender can set the **Don't Fragment (DF)** bit and let the network tell it when a packet is too large. When a router cannot forward a DF packet because the next link's MTU is smaller, it sends back ICMP type 3 code 4 with the MTU it can handle. The sender lowers its packet size and retries. This is **Path MTU Discovery**, and it is how TCP chooses a segment size that fits the whole path.

TCP's **MSS** is the MTU minus the IP and TCP headers: 1500 − 20 − 20 = 1460 bytes for ordinary Ethernet. That is why a TCP segment is usually 1460 bytes, not 1500. The MSS option is negotiated during the handshake so both sides agree on a size that fits.

<DeepDive title="Why blocking ICMP breaks the internet">Path MTU Discovery depends on ICMP. If a firewall drops all ICMP "fragmentation needed" messages, the sender never learns that its packet is too large. It keeps retrying the same size, the router keeps dropping it, and the connection hangs — a **PMTUD black hole**. The symptom is maddening: small requests work, large ones stall, and nothing in the logs says why. This is why network engineers say "don't block all ICMP"; you can rate-limit it, but you need the error types to get through. The same logic applies to IPv6, where routers never fragment and ICMPv6 Packet Too Big is mandatory.</DeepDive>

### IPv6 Changed the Rules

IPv4 lets routers fragment. IPv6 does not: only the source may fragment, and in practice it should not. Instead, every IPv6 host is expected to perform Path MTU Discovery, and routers send **ICMPv6 Packet Too Big** (type 2) when a packet will not fit. The minimum IPv6 MTU is 1280 bytes, so a host that cannot discover a larger value can always fall back to that.

This is a cleaner design — reassembly in routers was always a bottleneck — but it makes ICMPv6 even more essential. An IPv6 network that blocks it is not "hardened"; it is broken for large packets.

<Axiom>ICMP is not optional plumbing. It is how IP reports its own failures, and blocking it turns a diagnosable problem into a silent one.</Axiom>

## Frequently Asked Questions

**Does ICMP have ports?**
No. It is carried directly in IP and identified by type and code, not by a port number. That is one reason firewall rules for ICMP look different from TCP or UDP rules.

**Why does `ping` sometimes work but large downloads stall?**
That is the classic PMTUD black hole. Small packets fit; large packets need fragmentation or an ICMP error that is being blocked. The fix is to allow the relevant ICMP types, or to clamp the MSS on the router.

**Is fragmentation bad?**
It is not evil, but it is a sign that the sender and the path disagree about size. Modern networks try to avoid it with PMTUD and MSS clamping. Fragmentation still happens, especially with UDP, and it is worth recognizing in a capture.

**What is the difference between MTU and MSS?**
MTU is the largest IP packet a link can carry. MSS is the largest TCP payload a connection can send, derived from the MTU minus the IP and TCP headers. MTU is a link property; MSS is a TCP negotiation.

### Fun Facts and Notes

- The minimum IPv6 MTU is 1280 bytes, chosen so that every link can carry a full IPv6 header plus a reasonable payload without fragmentation.
- `traceroute` on Windows (`tracert`) uses ICMP echo requests; the Unix version often uses UDP packets to high ports. Both rely on Time Exceeded.
- Jumbo frames raise the MTU to 9000 bytes in data centers, but only when every device on the path agrees. One 1500-byte link in the middle turns a jumbo frame into a PMTUD problem.
- The "fragmentation needed" ICMP message includes the next-hop MTU precisely so the sender does not have to guess. Ignoring that field is how black holes are born.
